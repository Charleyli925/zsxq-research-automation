# ZSXQ 飞书通知策略

## 目标

群消息只回答四件事：哪一份飞书文档刚刚可读、本轮最终完成了什么、是否有需要关注的异常、异常是否已经恢复。扫描、等待、占锁、退避和逐文件进度保留在运行状态与日志中，不再占用群消息。

## 消息格式

单份文档完成后立即发送紧凑 Markdown，不重复列出文件名：

```markdown
## ✅ 知识星球研报｜文档 2/6 已发布

本批 **10** 篇｜累计发布 **20/51**

文档：[立即查看飞书文档](https://example.invalid/docx/demo-2)
```

全部批次结束后仍发送一条终态 Markdown：

```markdown
## ✅ 知识星球研报｜本轮完成

下载/待处理 **4**｜总结 **4**｜发布 **4**｜异常 **0**

文档：[飞书文档 1](https://example.invalid/docx/demo)
```

异常消息只保留异常文件、定位结果、可能原因、下一步动作和已生成的飞书链接。下载前预检会区分浏览器缺失、9223 调试端口不可用、CDP 假在线、知识星球登录失效、星球页面/网络异常，以及页面状态无法识别。可自动恢复的故障说明系统会重试；登录失效、权限不足、浏览器缺失等故障明确提示人工动作，不再统一宣称“无需处理”。用户消息不显示本机日志、JSON、缓存或隔离文件路径。

下载失败消息示例：

```markdown
## ⚠️ 知识星球研报｜下载异常

**检查区间**：07-16 10:37 → 07-16 12:00
**状态**：未完成
**定位结果**：浏览器进程和 9223 端口仍在，但 Playwright 接管浏览器超时。
**可能原因**：专用浏览器会话可能卡死，或 DevTools/CDP 通道处于假在线状态。
**建议处理**：系统会在后续窗口重试；若连续失败，请重启专用 Chrome for Testing。
```

## 可靠性与去重

- 下载和摘要分别使用独立持久 outbox；通知失败不会重新扫描、OCR、总结或发布。
- 飞书调用使用稳定幂等键，本地也记录已发送键。
- 每份文档通知使用独立 `document` supersede scope；最终汇总使用整批 `batch` scope。单文档任务中两条消息也不会互相覆盖。
- 同一轮仍有待投递的文档通知时，最终汇总暂缓投递；文档通知成功或进入 `dead_letter` 后再放行最终汇总，维持“文档链接在前、总结在后”的顺序。
- 每次任务运行默认只做一次飞书发送尝试，不在任务锁内做秒级同步重试；失败结果先持久化到 outbox，释放本轮后由后续定时运行继续投递。
- 首次发送失败后按 5、10、20 分钟退避；连续四次投递失败后进入 `dead_letter`，不再无限重试和占用任务锁，保留审计记录供人工检查。
- 下载侧相同异常 4 小时内不重复提醒，覆盖同一计划窗口里的分钟级重试；跨过下一个主要下载窗口仍失败时会再次提醒。异常签名包含原因和本轮处理进度，不同异常或受影响范围会生成新事件。
- 同一链路只保留最新的未投递结论：成功会取消尚未送达的旧异常，新的失败会取消尚未送达的旧恢复，新终态会 supersede 同批次旧终态，避免迟到消息与当前状态相反。
- 摘要侧同一批次、同一终态只投递一次；终态幂等键包含运行结论和失败阶段，部分完成后成功会产生新的成功终态。
- 历史超过飞书幂等字段长度限制的待投递键会在发送前迁移为短键。
- 状态、结果、重试账本和 outbox 均采用原子替换写入。

## 真相源

下载结果以固定扫描窗口、不可变 scan plan、UUID run manifest 和最终 canonical result 为准；不采信 Agent 自报数量来推进游标。候选文件若与资料库已有文件内容哈希相同，会记为“已在库内容重复”：它计入本轮对账完成数但不冒充新增下载，只有新增与已在库项合计覆盖全部候选时才推进游标。摘要结果以 `run_status.json`、`last_result.json`、逐阶段重试账本、发布记录和通知 outbox 联合判断，群消息只是展示层。

按 2026-07-08 至 2026-07-14 的发布量回放，恢复“每份文档一条、每轮再一条终态”后，正常周约 60–75 条；仍比旧基线 181 条减少约 60%，且不再发送逐文件、busy、等待和普通空跑消息。
